# 국내 결제수단별 자동화 가능성 조사

> 조사일: 2026-08-14. 공개 문서·개발 가이드·사용자 후기 기반. 실제 결제는
> 실행하지 않음. 세부 사실(도메인, 키패드 형태 등)은 실결제 네트워크 캡처로
> 재확인 필요.

## 핵심 결론 (요약)

**국내 주요 결제수단은 "자동화된 결제 승인"을 막도록 의도적으로 설계되어
있다.** 보안 키패드, 별도 기기 앱 인증(out-of-band), 생체인증은 우회 대상이
아니라 그 자체가 보안 기능이다. 따라서 "브로커가 결제 비밀번호를 웹에서 자동
입력한다"는 접근은 (1) 대부분 기술적으로 불가능하고, (2) 억지로 가능하게
만들려면 결제사 보안 통제를 무력화해야 하므로 약관 위반이자 사용자 계정
위험을 초래한다. **이 프로젝트는 그 방향을 채택하지 않는다.**

대신 결제사가 **공식적으로 제공하는 두 가지 정상 경로**로 자동화를 실현한다.

- **패턴 A — 빌링키/정기결제**: 최초 1회 사용자가 앱에서 본인인증 →
  빌링키(SID) 발급 → 이후 서버-투-서버로 사용자 개입 없이 결제. 브로커는
  원시 비밀을 만지지 않고 빌링키를 정책 통제 하에 사용. **진짜 무인
  자동화가 가능한 유일한 정상 경로.**
- **패턴 B — Human-in-the-loop 핸드오프**: 에이전트가 검색~체크아웃 진입까지
  수행하고, 최종 승인만 사용자 폰(앱 인증/생체)으로 넘김. 완전 무인은
  아니나 사용자 수고는 "지문 한 번"으로 축소되고 안전.

정책 임계값이 두 패턴의 분기점이 된다: **소액·구독형 → 패턴 A, 고액·일회성 →
패턴 B.**

**구현 타깃 확정**:
- **패턴 B(화면 클릭 + 폰 승인)**: 카카오페이 + 토스페이. 화면에선 결제수단
  선택 + 휴대폰번호/생년월일 + 다음까지만, 최종 승인은 폰. **최초 검증은 카카오**,
  토스는 동일 어댑터로 확장.
- **패턴 C(사전 승인 무마찰)**: 쿠팡 원터치. 인-페이지에서 [결제하기] 클릭만으로
  완결(비번·폰 승인 없음). 외부 게이트가 없어 정책+확인+통지가 게이트. 빌링키·
  가맹점 계약 없이 완전 핸즈오프가 되는 유일한 길. 카카오 다음 타깃.
- **네이버페이 제외** / 삼성페이는 고액 승인 수단(아래 "설계 반영" 참조).

## 결제수단별 비교표

> "완전 무인 웹 자동 결제"(화면에서 비밀까지 자동 입력) 기준. 이 열이 "불가"라도
> **패턴 B(화면 클릭 + 폰 승인)** 로는 카카오·토스가 가능하다 — 승인을 사람이
> 폰에서 하기 때문. 아래 "패턴 B 대상" 열로 구분한다.

| 결제수단 | 화면제어 자동 실행 | 패턴 | 인간 게이트 | 화면 입력 UI |
|---|---|---|---|---|
| **카카오페이** | ✅ **주력(최초 검증)** | B | 폰 생체(외부) | 휴대폰번호/생년월일(일반 input) |
| **쿠팡(쿠페이)** | ✅ **가장 쉬움(2번째)** | C | 없음 → 정책+확인+통지 | 없음(원터치, [결제하기] 클릭만) |
| **토스페이** | ✅ 지원(카카오 후 확장) | B | 폰 생체(외부) | 휴대폰번호/생년월일(일반 input) |
| 네이버페이 | ❌ 제외 | — | PC 웹에서 완결 | 6자리 보안 키패드 |
| 삼성페이·앱카드 | (고액 승인 수단) | (B 보조) | 폰 생체(FIDO/TEE) | 브라우저에 비밀 없음 |

> 쿠팡 패턴 C는 **원터치 결제 ON 전제**. 6자리 비밀번호 경로는 결제 비밀
> 저장/키패드 조작이 필요해 채택하지 않는다. 원터치가 아니면 대상 아님.

## 1. 토스페이

- **PC 웹**: `pay.toss.im`으로 전체 리다이렉트(iframe 미지원).
- **인증**: PC 웹은 휴대폰번호+생년월일 입력 → 토스 앱 푸시 → **앱에서 승인**.
  공식적으로 "웹 키보드 방식 웹결제 미제공". 웹에는 비밀 입력 UI가 없음.
- **자동화**: 단건 불가(승인이 앱 out-of-band). 빌링키 기반 정기결제만
  조건부 가능(최초 1회 앱 인증 전제, 가맹점 서버 모델).
- 참고: 토스페이먼츠(PG) 카드 직접입력은 보안 키보드+E2EE + 카드사 본인인증.
- 도메인: `pay.toss.im`, (PG) `js.tosspayments.com`, `api.tosspayments.com`
  외 카드사·CDN 다수.

## 2. 카카오페이

- **PC 웹**: `ready` API → `next_redirect_pc_url`(`online-payment.kakaopay.com`)을
  팝업 또는 리다이렉트로 표시.
- **인증**: QR 스캔 또는 카카오톡 푸시(휴대폰번호+생년월일 입력) → **최종
  승인(카드선택+6자리 비번+생체)은 별도 모바일 앱**. 웹 단독 완결 경로 없음.
- **입력 UI**: PC 결제창 초기 입력(휴대폰번호/생년월일)은 일반 DOM input
  (공개 오토필 확장이 `#phoneNumber`, `#dateOfBirth` 채움 확인). 비번은 앱.
- **자동화**: 단건 불가. **SID 빌링(정기결제)**은 최초 1회 앱 인증 후
  `customer_uid`로 서버-투-서버 재결제 → 조건부 가능.
- 도메인: `online-payment.kakaopay.com`, `pay-api-gw.kakaopay.com`,
  `kapi.kakao.com`, `pay.kakao.com`, `qr-kakaopay.kakao.com`.

## 3. 네이버페이

- **PC 웹**: `pay.naver.com` 팝업 윈도우(모바일은 리다이렉트).
- **인증**: 6자리 결제 비밀번호를 **PC 웹에서 직접 입력하는 경로가 존재**
  (카카오/토스와 차별점 — 앱 푸시 불필요). 단, 네이버 로그인 세션 + 결제수단
  등록 + 비번 설정 전제.
- **입력 UI (결정적 변수)**: 정황상 **마우스 클릭식 보안 키패드**로 추정,
  랜덤 배치/E2E 여부 미확정. 보안 키패드라면 `input.value` 주입이 통하지
  않고, `isTrusted` 요구·캡처 방지가 있으면 합성 클릭도 거부됨 → **표준 DOM
  자동 입력은 사실상 불가**. (이 통제를 뚫는 방향은 채택하지 않음.)
- **2FA**: 비번 5회 오류 잠금, 새 기기 로그인 시 계정 2단계 인증 가능.
- **자동화**: 웹 비번 경로는 있으나 보안 키패드로 사실상 불가. 정상 경로는
  자동결제/정기결제 등록.
- 도메인: `pay.naver.com`, `m.pay.naver.com`, `nid.naver.com`(로그인),
  `apis.naver.com`, `pstatic.net`(CDN). 피싱 사칭 사이트 다수 → 정식
  도메인만 화이트리스트.

## 4. 쿠페이 (쿠팡페이)

- **PC 웹**: 외부 PG 리다이렉트 없이 **쿠팡 체크아웃 인-페이지**에서 처리.
- **인증**: PC 표준은 6자리 결제 비밀번호. 생체/원터치 "설정"은 앱 전용.
  원터치 활성 시 로그인 세션만으로 비번 없이 확정 가능(단, 쿠팡 리스크
  기준에 따라 비번 재요구 가능).
- **입력 UI**: 일반 input인지 랜덤 키패드인지 **공개 문서로 미확정**(실측 필요).
- **제약**: 현재 **쿠팡 생태계 전용**(외부 가맹점 확장은 예정 단계). 범용
  쇼핑 대행에는 부적합.
- **자동화**: 조건부. 사용자가 앱에서 명시적으로 켠 원터치 결제를 활용하는
  것이 정도(우회가 아니라 사용자가 허용해둔 저마찰 경로).
- 도메인: `coupang.com`, `login.coupang.com`, `pay.coupang.com`(내부 추정),
  `coupangpay.com`.

## 5. 삼성페이 / 삼성 앱카드

- **삼성페이(삼성월렛) 웹결제**: 결제창에서 삼성페이 선택 → 휴대폰번호
  입력/QR → 폰 푸시 → **폰에서 생체/비번 승인**.
- **삼성 앱카드**: 결제창에서 앱카드 선택 → 폰에서 앱 실행 → QR/7자리 코드
  → **폰에서 비번/생체 승인**.
- **승인 위치**: 둘 다 최종 승인이 폰 생체(FIDO/TEE). **브라우저에 결제
  비밀이 전혀 없음** → 매 결제 폰 조작(HITL) 구조적 강제.
- **자동화**: 불가. 격리 관점에선 완벽하나 바로 그 때문에 무인 자동화와 충돌.
  → **고액 결제의 HITL 승인 수단으로 활용**(패턴 B).
- 참고: 카드번호 직접입력형(일반결제/안심클릭)은 조건부지만 (1) 30만원 이상
  인증서/ARS, (2) 보안 키패드, (3) 카드번호·CVC 평문 보관 리스크(민감정보,
  더미/토큰만 사용). 권장하지 않음.

## 설계 반영

1. **패턴 B 실현 대상 = 카카오페이 + 토스페이 (phone-push형).** 화면에서 하는
   일이 "결제수단 선택 + 휴대폰번호/생년월일(평문) + 다음" 뿐이고 진짜 승인은
   폰에서 사람이 한다 → 화면에 결제 비밀이 없어 우리 격리·무우회 원칙에 부합.
   **둘 다 지원**하되 구조가 동일하므로 카카오 어댑터를 먼저 만들고 토스는
   같은 인터페이스로 확장한다.
2. **네이버페이는 패턴 B에서 제외.** PC 기본 경로가 화면 6자리 보안 키패드
   입력(승인이 PC에서 완결)이라, 자동화하려면 (a) 결제 비밀 보관 + (b) 키패드
   합성 클릭이 필요 → 아래 "채택하지 않는 것"에 정면 위배. "화면 클릭 + 폰
   승인" 안전 구조도 성립하지 않음.
3. **결제창은 에이전트가 아니라 브로커가 인수.** [결제하기]까지는 에이전트,
   결제사 창부터는 브로커가 제어 → 식별정보 입력·완료 파싱이 신뢰 영역에
   머문다. (MCP/스킬 통합이면 자연스럽게 강제 — AGENTS.md §2.6)
4. **패턴 C 대상 = 쿠팡 원터치.** 인-페이지 같은 origin이라 화면 제어가 가장
   쉽고, [결제하기] 클릭만으로 완결. **외부 인간 게이트가 없으므로** 안전은
   정책+우리 확인(confirm)+즉시 통지가 담당. 빌링키·가맹점 계약 없이 완전
   핸즈오프가 되는 유일한 길이라 지정가 감시 플래그십에 적합. **원터치 ON
   전제, 6자리 비번 경로는 금지.** 카카오 다음 타깃.
5. **패턴 A(빌링키)는 후순위** — 지정 가맹점 구독 시나리오에서만. 카카오 SID 등.
6. **채택하지 않는 것**: 보안 키패드 우회, 합성 클릭으로 키패드 입력,
   FDS/안티봇 회피, 카드번호·CVC 평문 보관/자동입력, 쿠팡 6자리 비번 경로.
   결제사 보안 통제를 무력화하는 모든 접근.

## 패턴 B 실제 결제 플로우 (카카오페이 — 최초 검증 타깃)

```
[쇼핑몰 체크아웃]
 1. Agent: "카카오페이" 선택 → [결제하기] → 결제창 열림
           (online-payment.kakaopay.com)  ← 여기서 Broker가 인수
 2. Broker: 휴대폰번호 + 생년월일 입력(사용자 프로필, 평문 input) → [다음]
           ※ PII이지 결제 비밀 아님. 카드번호·비번은 이 화면에 없음.
 3. Broker → 사용자: 익스텐션 알림 "△△몰 ₩28,900 — 폰에서 카카오페이 승인"
 4. 사용자(폰): 카톡 → 카카오페이 → 카드 선택 → 지문/PIN  ← 진짜 승인 게이트
    (결제사 푸시 자체가 승인 게이트. 별도 승인 채널 불필요)
 5. Broker: 쇼핑몰 완료 페이지 주문번호/성공 신호 독립 파싱
 6. Broker: chrome.notifications "결제 완료 ₩28,900, 주문 #12345" + 감사 로그
```

토스페이도 동일 구조(휴대폰번호/생년월일 → 토스 앱 푸시 → 폰 승인). 카카오
어댑터 검증 후 같은 `SimplePayAdapter` 인터페이스로 토스 어댑터 추가.

## 패턴 C 실제 결제 플로우 (쿠팡 원터치)

```
[쿠팡 체크아웃 — 인-페이지, 같은 origin]
 1. Agent: 상품 선택 → 결제수단 "쿠페이(원터치)" 확인 → 정책 검증 요청
 2. Broker: verify()로 결제 예정 금액 파싱 → policy.evaluate
      - 임계값 초과/비지정 구매 → confirm (익스텐션에서 사용자 확인)
      - 정책 내 지정 구매 → allow
 3. Broker: [결제하기] 클릭  ← 비번·폰 승인 없음(원터치)
      ※ 6자리 비번 UI가 뜨면 즉시 중단(failed) — 비번 미입력
 4. Broker: 주문완료 화면/주문번호 독립 파싱
 5. Broker: chrome.notifications "결제 완료 ₩28,900, 주문 #..." + 감사 로그
```

> 외부 인간 게이트가 없으므로 3단계 전 confirm 게이트와 5단계 즉시 통지가
