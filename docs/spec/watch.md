# Spec: 감시 엔진 (폐기됨, 2026-09-23)

> **이 모듈은 제거됐다.** `broker-extension/src/watch/`, 관련 RPC
> (`addWatch`/`removeWatch`/`pauseWatch`), 사이드패널 "감시" 탭이 모두
> 삭제됐다. 아래는 왜 제거했는지와 지금 같은 역할을 무엇이 대신하는지의
> 기록이다 — 새 구현을 만들 때 이 문서를 되살리지 말 것.

## 왜 제거했나

1. **실제로 작동하지 않았다.** `compose.ts`의 `priceReader()`가 항상
   `{ price: Infinity, inStock: false }`를 반환하는 하드코딩 스텁이었다 —
   상품 페이지의 실제 가격·재고를 파싱하는 로직이 애초에 구현된 적이 없어서,
   등록된 감시는 조건을 절대 충족할 수 없었다(영원히 "watching" 상태).
2. **M2(MCP 브리지)가 같은 책임을 더 유연하게 대신한다.** 플래그십 시나리오
   (AGENTS §1.1 "지정가 자동 구매")가 원래 상정한 "에이전트: 지정 상품의
   가격·재고 모니터링"은 이제 Claude Code가 `open()`/`read_page()`로 직접
   가격을 확인하는 방식으로 구현 가능하다 — 폴링 주기·조건 판단(가격 외에도
   재고·옵션·리뷰 등 임의 조건)을 스킬(두뇌)이 자유롭게 정할 수 있어 익스텐션
   내장 폴러보다 범용적이다. 반복 실행은 사용자가 Claude Code를 다시 부르거나
   `/schedule` 같은 크론으로 스킬을 주기 호출하면 된다.
3. **결제 게이트는 그대로 유지된다.** 감시가 없어져도 `request_payment`는
   여전히 정책 엔진 + confirm 게이트를 거친다(`docs/spec/mcp-integration.md`,
   `docs/spec/broker-api.md`) — 안전 경계는 이 모듈에 있던 적이 없다.

## 다시 만들게 된다면

- **먼저 가격 파싱을 실제로 구현할 것.** 스텁 상태로 UI만 노출하지 말 것 —
  이번 제거의 핵심 원인이 "안 되는 기능이 되는 것처럼 보였다"는 것이다.
- 사이트별 파싱이 필요하므로(`executor/selector.ts`의 텍스트/라벨 앵커
  셀렉터 스킴 참고), 익스텐션 내장 폴러로 다시 만들지, 에이전트 쪽(스케줄된
  스킬 호출)에 맡길지부터 재검토할 것 — 후자가 이미 더 유연하다는 게 이번
  제거의 결론이었다.
