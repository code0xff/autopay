# 개발 방법론 (Methodology)

> 목표: **문서만으로 처음부터 끝까지 개발 가능**. 코드는 스펙을 구현·검증하는
> 산출물이고, 스펙이 먼저다.

## 1. 스펙 주도 개발 (Spec-Driven Development)

모든 모듈은 코드보다 **스펙 문서(`docs/spec/<module>.md`)가 먼저** 존재한다.
스펙은 다음을 반드시 포함한다.

1. **목적(Purpose)** — 이 모듈이 무엇을 책임지나, 무엇을 안 하나.
2. **입출력 계약(Contract)** — 함수/메시지의 타입(가능하면 `shared`의 Zod
   스키마 참조). 신뢰 수준(Trusted/Untrusted/경계)을 명시.
3. **불변식(Invariants)** — 항상 참이어야 하는 조건 (예: "정책 위반 요청은
   절대 approved를 반환하지 않는다", "비밀은 로그에 남지 않는다").
4. **수용 기준(Acceptance Criteria)** — 완료 판정 체크리스트.
5. **테스트 케이스(Test Cases)** — 정상/경계/실패 케이스 목록. 이게 곧
   Vitest 테스트의 명세가 된다.

스펙과 코드가 충돌하면 **스펙이 진실**이다. 구현 중 스펙이 틀렸음을 알게
되면 코드가 아니라 스펙을 먼저 고치고, 그 다음 코드를 맞춘다.

## 2. TDD (정책 엔진·순수 로직 우선)

정책 엔진은 `(request, policy, history) → decision` 순수 함수다. 여기에
가장 두터운 테스트를 둔다. 순서:

1. 스펙의 테스트 케이스를 Vitest로 먼저 작성(실패 확인).
2. 통과하는 최소 구현.
3. 리팩터. 부수효과 없음 유지.

경계면(브로커 API, executor)은 통합/E2E 테스트(Playwright)로 보완한다.

## 3. 신뢰 경계 규칙 (필수)

- **경계를 넘는 모든 메시지는 `shared`의 Zod 스키마로 검증.** 파싱 실패 =
  즉시 거절(reject). 검증되지 않은 데이터는 신뢰 영역에 진입 불가.
- executor/vault(refstore) 관련 변경은 PR 설명에 "이 변경으로 비밀·빌링키가
  API·로그·DOM 밖으로 나갈 수 있는가?"에 답을 적는다. (AGENTS.md §4)
- 새 정책 필드의 기본값은 항상 가장 제한적(deny).

## 4. Definition of Done (DoD)

한 작업(모듈/기능)이 "완료"되려면:

- [ ] `docs/spec/<module>.md` 존재하고 최신 상태
- [ ] 스펙의 테스트 케이스가 Vitest/Playwright로 구현됨
- [ ] 구현이 모든 테스트를 통과
- [ ] 경계 메시지는 Zod 검증을 거침
- [ ] 비밀/PII가 로그·에러·커밋에 없음 (grep 확인)
- [ ] typecheck(`tsc --noEmit`) + lint(Biome) 통과
- [ ] PR 설명이 해당 스펙을 참조

## 5. Git / 협업 워크플로

- **기본 브랜치 = `dev`.** 일상 작업은 `dev`에서 관리한다(`main`은 릴리스용).
- **커밋 단위 = 기능 완결성.** 중간중간 "기능적으로 완결된 지점"마다 커밋한다
  (반쯤 된 상태 커밋 금지). 한 커밋은 그 자체로 빌드·테스트가 통과해야 한다.
- **기능 완결 시 Codex 리뷰.** 기능이 완결되는 지점(≈커밋/마일스톤)마다
  Codex 리뷰를 돌려 2차 검토를 받는다(코드 품질·버그·격리 원칙 위반 점검).
  리뷰 지적 반영 후 커밋한다.
- 커밋 메시지는 Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`,
  `refactor:`).
- 큰 단위는 feature 브랜치 → `dev`로 PR, 관련 스펙 문서 링크 + DoD 체크리스트.
- CI(typecheck+lint+test) 통과가 머지 조건.

## 6. 코딩 에이전트(Claude Code/Codex)를 위한 지침

- 작업 착수 전 AGENTS.md(§0 포지셔닝, §2.5/§2.6 결제·격리 모델)와 해당
  `docs/spec/<module>.md`를 읽는다.
- 스펙이 없으면 코드부터 쓰지 말고 스펙을 먼저 제안한다.
- 결제사 보안 통제 우회(키패드 합성 클릭, FDS 회피 등)는 금지(§2.5). 이런
  방향이 필요해 보이면 진행 대신 사용자에게 설계 재검토를 요청한다.
